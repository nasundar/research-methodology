# Case study — L1.21 case 1: arithmetic + package names

> **Source.** Anchor paper rev-18 → rev-19 → rev-20 in the seed session
> (`data-pilot-research`). Specifics redacted to highlight the
> *pattern*; the seed session's actual content is not reproduced here.

> **Purpose.** Calibrate intuition for the L1.21 anti-pattern
> (playbook 07) in its classical "base case" form: an agent closes
> major substantive reviewer findings successfully, while
> introducing new execution-class bugs in the same revision.

---

## Setup

A research paper had reached its 5th major revision. Standing reviewers
(a Claude variant + a GPT variant, playbook 08) had been reviewing for
4 cycles. The revision goal was substantive: fold two new experiments
that close 2 standing major-revision threads.

## Rev-18 (closes 2 major threads, introduces 2 new A1 bugs)

The revision agent successfully landed the two new experiments. The
substantive content — the load-bearing claim — landed correctly. The
4-cycle major thread closed. By the substantive content's measure,
this was a successful revision.

But the same revision introduced two execution-class bugs:

### Bug class 1 — Arithmetic on new event totals

The new 3-component mix was reported with component counts
`1M + 1M + 0.91M = 2.74M`. The correct sum is
`1,000,000 + 1,000,000 + 909,090 = 2,909,090`, not `2,740,000`. The
total was off by 170K events; the column-sum mass attribution was off
by 6.2%.

This is the prototypical L1.21 bug: a number the agent had to author
from scratch to summarise the new content. The agent prioritised
landing the substantive claim and didn't recompute the headline
arithmetic against the source numbers.

### Bug class 2 — Wrong package names in a Commands column

A section that documented "how to reproduce this experiment" instructed
the reader to run a bench in package `dp-research-reality`, when the
actual package is `dp-research-candidates`. Readers cannot reproduce
the bench at all. The agent had to re-emit this Commands column after
restructuring an adjacent section; in re-emitting it, the package
name got attributed to the wrong package.

### What the reviewers caught

- Reviewer A (the Claude variant): **MISSED both bugs**. Returned
  MINOR / recommend ACCEPT with 0 A1, 1 A2, 3 A3. The Claude
  reviewer's strength is internal-math verification and overclaim-
  catching — neither bug here triggered those instincts.
- Reviewer B (the GPT variant): **CAUGHT both as A1 (blocking)**.
  Verdict: MAJOR REVISIONS specifically because of the two new bugs.

This is the single-reviewer-protocol-insufficient case study compressed
into one revision: had the team used only reviewer A, they would have
graduated rev-18 with both bugs. The pair caught it.

## Rev-19 (closes the rev-18 bugs structurally, introduces 2 new A1 bugs)

The next revision agent fixed both rev-18 bugs structurally:

- The arithmetic was redone with the correct count.
- The package name in the Commands column was corrected.

The substantive story strengthened further — the team also folded a
follow-up experiment that confirmed the result.

But rev-19 introduced **two new** execution-class bugs of *different
classes*:

### New bug 1 — Band attribution drift

The paper stated "pre-registered ±25%" in 5+ locations referring to a
specific hypothesis. The hypothesis was actually pre-registered at
**±30%** in `HYPOTHESIS.md`. The 5-site repetition meant the same
wrong band attribution propagated through the whole paper. Both
reviewers caught this independently in their own cycles.

### New bug 2 — Same bug class, different cell

The exact bug from rev-18 (wrong package names in the Commands column)
was *structurally* closed in rev-19, but a *new* variant of the same
bug appeared on a *different row* of the same Commands table. The
row's test name was wrong; the env-var spellings were wrong (singular
vs. plural; wrong substring).

This is the "same bug class, different cell" telltale of L1.21
(playbook 07). The agent had patched the specific cell the reviewer
flagged but had not re-audited adjacent cells in the same structural
location.

## Rev-20 (the graduation revision under V1–V5)

By rev-20 the team had named the pattern (L1.21) and added the first
version of the verification protocol (V1–V5; V6 was added later, see
case study 2). The revision-agent prompt now included five mandatory
pre-commit steps:

- V1: grep for surviving literal wrong claims by string.
- V2: grep for surviving counter-claims.
- V3: cross-check each numerical claim against source.
- V4: re-verify the abstract and TL;DR.
- V5: word-count and header-count audit.

The agent passed V1–V5 cleanly with **one microscopic A3-class
leftover** — one supplement bullet item still had the old arithmetic
totalised number as a quotable string. This was caught by reviewer A
as A3 (cosmetic), reviewer B as ACCEPT-with-no-finding.

Verdict: reviewer A **ACCEPT / GRADUATE** (the first ACCEPT in 7
cycles). Reviewer B **MINOR for both venues** (down from MAJOR/MINOR
mixed at the prior cycle).

The L1.21 pattern broke for the first time at rev-20. The protocol
was working.

## Lessons extracted

1. **L1.21 is real and persistent.** Three consecutive revisions
   introduced new bugs each time. The bugs shrank in surface area
   (170K-event arithmetic error → 5-site band attribution → one-
   string-leftover cosmetic) but they did not vanish.
2. **The reviewer pair is necessary, not optional.** Reviewer A
   missed the rev-18 bugs entirely; the team would have graduated
   on a falsely-positive single-reviewer ACCEPT.
3. **V1–V5 broke the pattern.** Rev-20 (the first revision under the
   protocol) produced exactly one cosmetic leftover and zero
   substantive bugs.
4. **"Same bug class, different cell" is a telltale**, not noise.
   When a reviewer flags wrong package names in row 5 and the next
   revision has wrong package names in row 7, the team is in L1.21
   territory and needs the protocol.

## What to do if you see this pattern

Apply the V1–V6 protocol (playbook 06). Specifically:

- Pre-cycle: emit the V1/V2 grep templates **for the bugs caught
  this cycle**.
- Mid-revision: every new constant or number gets a "where else does
  this appear?" enumeration before commit.
- Post-revision (pre-push): run V1–V6 verbatim.

Expect the pattern to *take 2–3 cycles to break* even with the
protocol — V1–V6 itself grows as new bug classes escape.
