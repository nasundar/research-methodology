# Playbook 07 — The L1.21 Anti-Pattern

> An agent-driven paper revision reliably **closes the bugs the reviewer
> flagged** while **introducing new bugs at the same time**. The bugs
> shrink in surface area across cycles but they do not vanish. Untreated,
> the cycle does not terminate. This playbook names the pattern, shows
> how to recognise it, and describes the mitigation.

## The pattern

Across ten consecutive revisions of two unrelated papers in the seed
session, every revision exhibited the following structure:

1. The agent receives a reviewer report with N findings.
2. The agent closes all N findings substantively.
3. **In closing them, the agent introduces M new findings.**
4. The new findings are smaller in scale than the old ones but they
   are real, reviewer-detectable bugs.
5. Without an explicit verification protocol, the cycle never converges
   on its own — there's always a next-smallest bug class that becomes
   the marginal failure mode.

The seed session entered the lesson into its knowledge ledger as `L1.21`.
We label the pattern with the same identifier here for continuity.

## Why it happens

Three mechanisms compound:

### 1. Cognitive scope at revision time

The revision agent's attention is *on the open findings*. It's writing
new content to close them. The content elsewhere in the paper — the
content the prior reviewers signed off on — is "background", and the
agent's checks on background sections are shallower than its checks on
the diff. When the revision touches a table cell, a Commands column, or
a constant that appears in a section the agent considers background,
the touch can introduce drift without the agent noticing.

### 2. Focus on substantive completeness over consistency

When the revision must close a major finding (e.g., "run a new
experiment, fold its results into the paper"), the agent prioritises
**substantive completeness** — the new content lands correctly and the
load-bearing claim updates appropriately. The same agent has less
attention available for **execution consistency** — arithmetic, package
names, cross-references, denominator conventions. The substantive bugs
get closed; the execution bugs slip in.

### 3. Bug surface area shrinks but the discipline doesn't scale

Each L1.21 recurrence is *smaller* than the last (arithmetic errors →
wrong env-vars → wrong band attribution → cross-section inconsistency
→ denominator convention). The next-smallest bug class becomes the
marginal failure mode. The team is correctly closing increasingly
subtle bugs, but the next-subtler bug class always exists.

## How to recognise L1.21 in your own work

Three telltales:

| Telltale | What it looks like |
|---|---|
| **Verdict swap** | One reviewer's verdict improves; another's worsens. Same revision, opposite trajectories. |
| **Same bug class, different cell** | Reviewer flagged "wrong package name in Table 3 row 5"; revision fixes Table 3 row 5; **Table 3 row 7** now has a *different* wrong package name. |
| **Sign-preserving magnitude shift** | The direction of a number is correct; the magnitude is off because of a denominator convention or a constant attribution drift. Direction-only checks pass; reviewers catch the magnitude. |

If you see any of these three in a revision cycle, you are in L1.21
territory. The right response is not "try harder" — it's to add the
appropriate V-step to playbook 06 and re-run.

## The mitigation: V1–V6

The protocol that breaks L1.21 is described in detail in playbook
**06-V1-V6-verification**. The short version:

- **V1** catches literal leftover wrong claims.
- **V2** catches surviving counter-claims.
- **V3** catches cross-section inconsistencies (the bug class that
  motivated V3 was the "same bug class, different cell" telltale).
- **V4** catches numerical recomputation errors, including denominator
  convention drift (the bug class that motivated V4-extended was the
  "sign-preserving magnitude shift" telltale).
- **V5** catches undisclosed scope drift.
- **V6** catches stale code references.

The protocol is **monotone-extensible**: when a new bug class escapes
the existing steps, add a new step and prepend it to all future
dispatch prompts. V3 and V4-extended both arose this way.

## How to dispatch a revision agent under L1.21 discipline

The revision-agent prompt **must** contain, at the end:

```
Before committing, run V1–V6 per playbook 06. Emit the output of each
step in your reply. Do not commit if any step reports a finding that
contradicts the revision's stated claims.

For the bug classes the previous review surfaced, accumulate V1/V2
grep templates and apply them to this revision. The templates are
in <project>/.protocols/V1V2-templates.md (or accumulate inline
in your reply).
```

The orchestrator owns the V1/V2 template list and prepends it to every
dispatch. Each cycle, new templates are added from that cycle's caught
bugs.

## What "graduation" looks like under L1.21 discipline

When the protocol is working, a revision produces:

- **Zero new A1-class bugs** (the substantive load-bearing kind).
- **Zero new A2-class bugs** (substantive but non-blocking).
- **At most 1–3 A3-class cosmetic leftovers** (typos, formatting).

The reviewer pair returns:

- Reviewer A: ACCEPT (or ACCEPT with 1–3 cosmetic nits).
- Reviewer B: ACCEPT (or MINOR with 1 disclosure).

Two consecutive cycles at this verdict floor mean the paper has
graduated. See playbook **13-paper-graduation** for the full
verdict-trajectory model.

## Anti-patterns when responding to L1.21

- **"Try harder next revision."** L1.21 is structural, not effort-related.
  Adding effort without a layered audit reproduces the pattern at a
  smaller scale.
- **"Add a checklist to the agent prompt."** A checklist of bullets
  without grep templates and numerical recomputation is performative.
  V1–V6 works because each step does a concrete verifiable thing,
  not because it reminds the agent to be careful.
- **"Get a better reviewer."** Single-reviewer protocols cannot detect
  L1.21 because the bug introduced in cycle N is precisely the bug
  the reviewer did *not* flag in cycle N-1. You need either a
  reviewer pair (playbook 08) or a programmatic V1–V6 audit, and
  ideally both.

## When to stop adding V-steps

When the marginal new bug class is genuinely cosmetic (typos, comma
placement) and the team decides the cost of driving cosmetics to zero
exceeds the value, **document the floor explicitly**: "V6 is the last
step we run; A3-class cosmetic leftovers are accepted." This is fine.
What's not fine is silently letting A2-class substantive bugs through
because "we ran V6 once and it was clean".
